# LLM 与 Agent 的记忆机制

在谈论这个问题前，我们先给出结论：

> 一次普通的 Transformer API 调用通常是无状态的：模型不会在请求结束后自动保存这次对话。跨请求“记住”用户，通常依赖应用保存并重新提供历史或外部记忆。模型权重本身则承载训练获得的长期知识，但不是可按用户实时读写的会话记忆。

Transformer decoder-only 做的事只有一件：给定一串 token 序列，输出下一个 token 的概率分布。

## 模型原生“记忆”的边界

它内部的“记忆”只有两种：

1. 权重里面的知识

   训练时学到的世界知识、语言规律、常识，存在权重矩阵里。这是静态知识，不是对话层面的“记忆”。

2. 当前前向或解码过程中的临时状态

   推理时，输入序列经过 Attention、FFN 得到隐状态；增量解码还可能保留 KV Cache。下一个 token 可以利用注意力允许范围内的上文，但这些状态默认只属于当前请求，服务端是否跨请求保留状态取决于具体 API 与应用设计。

所以，对标准 Transformer 来说，没有类似数据库那样可由应用随时增删改查的用户记忆区。不能把“权重知识”“当前上下文”和“外部持久记忆”混为一谈。

## 上下文拼接：短期记忆

我们和大模型聊天，它能够记得上一句，靠的是最简单粗暴的方法：

上下文拼接（Context Concatenation）

每次我们发新的消息，系统都会做一件事：

> **把历史对话 + 系统提示 + 新问题，拼成一整段 prompt 喂给模型**。

模型看到的是完整序列，于是 “看起来” 记住了上文。

本质是：把记忆塞回输入里。

上下文窗口有模型训练范围和服务配置上限，也受位置编码、显存和推理实现约束。有些模型可以通过位置缩放或继续训练扩展窗口，但不能在推理时任意调大并期待质量不变。输入超限时，API 可能报错或按产品策略截断；应用通常需要先做截断、总结或检索。

工程师们早就考虑到了这个问题，当对话很长、需要跨会话记忆，就必须用外部系统，我们称为超过上下文窗口的 “长期记忆”。

## 外部记忆：向量数据库与 RAG

目前最主流、最成熟的 “外部记忆” 方案是： 向量数据库 + 检索增强（RAG）。

流程如下：

1. 把历史对话、文档、用户信息切成 chunk。
2. 用 embedding 模型转成向量。
3. 存入向量数据库（FAISS、Milvus、Chroma、Pinecone 等）。
4. 每次新问题 → 生成 query 向量 → 检索相关记忆片段。
5. 把检索结果拼进 prompt → 模型 “看到记忆”。

这种外部存储可以独立扩容、删除和更新，但容量、索引成本与检索质量都有边界；“存得下”也不等于“检索得到”或“模型会正确使用”。它是一种可管理的持久记忆实现，而不是无限且自动可靠的记忆。

## RAG 的上下文窗口问题

当然，我想你也想到了这个问题：拼成的新的 prompt 难道就不会超过上下文窗口了吗？

会，而且非常常见，甚至是 RAG 系统里最经典、最头疼的问题之一。哪怕现在窗口动辄 128k、200k 甚至 1M，照样会超。

RAG 的流程是：

> 用户问题 → 检索 N 段相关文档 → 全部拼进 prompt → 喂模型

这里有几个固定占用长度的部分：

- 系统提示（system prompt）
- 历史对话（chat history）
- 检索回来的文档（retrieved chunks）
- 用户当前问题
- 模型还要预留长度给输出回答

这些加起来，很容易就爆掉 context window。哪怕窗口是 128k，只要：检索段落多一点、文档长一点、对话历史久一点，直接溢出是常态。

那么超了之后会发生什么？

不同框架、模型处理方式不一样，但结果都很烂：

1. 自动截断（最常见）：从前面或后面直接切掉，关键信息直接丢。
2. 报错，拒绝生成。
3. 即使没有超限，过多低相关内容也可能干扰检索与推理；但效果不会仅因为接近窗口上限就必然“暴跌”，需要用具体模型和任务评测。

所以RAG 不是越长越好，而是刚好够且不超最好。

## 工业界的长度控制方法

那么工业界怎么解决 “检索后超窗口” 问题？

嘿嘿！😜

工程师们又考虑到了。

这一套是专门领域的标准技术，有专业名词：

1. Post-Reranking（重排序）

   先召回一大堆，再用小模型打分，只保留Top-K 最相关的片段。控制数量，从源头控制长度。

2. Context Compression（上下文压缩）

   专业名词就叫这个。对检索片段做摘要压缩，只保留和问题相关的句子，去掉冗余、无关内容。

3. Dynamic Prompt Truncation（动态截断）

   智能裁剪，而不是暴力切：保留最新对话，保留高相关性文档，丢掉不重要的历史。

4. Chunk 大小自适应

   小问题用小 chunk，大问题用长 chunk，避免一上来就塞爆。

5. Multi-Stage / Hierarchical RAG

   先粗查 → 再精查 → 再压缩 → 最后才拼 prompt。一层层控制长度。

成熟 RAG 系统通常会组合召回数量控制、token budget、元数据过滤、重排序和上下文压缩，但并非每套系统都默认启用 reranker，简单场景也可能只使用向量检索与 Top-K。

为什么是 Reranking（重排序）排第一？

原因很现实：不能把所有检索结果都塞进上下文，必须在 token budget 内选择片段。常见做法是 embedding 粗召回后用 cross-encoder 或模型重排。重排序本身不改写原文，因此没有摘要式压缩的改写风险，但仍可能把真正相关的片段排低或漏掉，必须结合检索指标与端到端回答质量评估。

## 结构化记忆

除了我们上述讨论的 RAG 外，还有一些方案例如结构化记忆（Key-Value / 记忆图谱），就是把记忆存成结构化数据：

- 用户偏好：{“喜欢咖啡”:“美式”}
- 任务状态：{“当前任务”:“订机票”，“目的地”:“北京”}
- 记忆条目：时间戳 + 内容 + 重要度 + 标签

推理时：根据当前问题检索相关条目，格式化塞进 prompt，这更像更像传统 AI 的 “状态机 + 记忆库”。

结构化记忆尤其适合用户偏好、任务状态、权限和业务实体等需要精确更新的内容，实践中常与向量检索组合使用。

## 研究中的记忆组件

现在也有很多论文试图给 Transformer 加真正的记忆组件，例如：

- Memory Transformer / 外部记忆库
- Recurrent Memory / 滑动窗口记忆
- 可训练的记忆 token（Memory Prompt）
- ......

这类方法从研究原型到流式推理、长上下文和 Agent 状态管理都有不同程度的应用；是否值得采用取决于任务，不能统一归为“尚未落地”。
